# personal-site

A personal technical folio: a static site generated by a small Haskell
executable that renders HTML with [Brigid](https://github.com/AugmenTab/brigid).
The visual language is dark Art Deco noir after the *Eclipsing Eden* brand.

**Current state: Phase 02 (typed content pipeline and safe Markdown)
submitted for owner review.** Pages are generated through one shared Brigid
shell:

- the approved Phase 00 homepage;
- a Work index;
- one page per published project, loaded from `content/projects/` (JSON
  metadata and a Markdown body);
- an About page;
- a 404 document;
- a Writing section, generated only when published articles exist (none
  do yet).

Phase retrospectives are kept locally in `.local/retros/phase-NN.md`
(git-ignored). The committed evidence is in [`design/proof/`](design/proof/).
The Phase 00 gate report is [`DESIGN_GATE.md`](DESIGN_GATE.md), and
the approved visual baseline is in [`design/regression/`](design/regression/).
Design decisions are recorded in [`docs/adr/`](docs/adr/).

## Requirements

Docker Engine and Docker Compose v2. Nothing else: GHC, Stack, Cabal and all
Haskell dependencies live in the container. Screenshot tooling also runs in a
container.

## Commands

```sh
docker compose build site-build                 # build the toolchain image (~1 min)
docker compose run --rm site-build              # compile + build the site into dist/
docker compose run --rm site-build stack exec -- site check   # validate only; writes nothing
docker compose run --rm site-build stack test   # Haskell tests
docker compose up -d preview                    # serve dist/ at http://localhost:8080/
docker compose run --rm site-build bash         # shell in the toolchain container

# development-only: screenshots + browser checks for every page into design/proof/
docker compose up -d preview
docker compose --profile tools run --rm screenshots
docker compose --profile tools run --rm art python3 tools/art/regression.py   # homepage vs approved baseline
```

`site-build` runs [`docker/build-site.sh`](docker/build-site.sh), i.e.
`stack build` followed by `stack exec -- site build --out dist`.

### The `site` CLI

| Command | Effect | Exit status |
| --- | --- | --- |
| `site build [--out DIR]` | Validate everything, render into `DIR.tmp/`, verify, then publish into `DIR` (default `dist`) | 0 on success; 1 with a `Build failed: …` message, leaving `DIR` untouched |
| `site check` | The same validation as `build` (content, routes, output paths, assets, media, stylesheets, rendered pages and links). Prints the output manifest and writes nothing | 0 if valid, 1 otherwise |

Run it inside the container, from the repository root (it reads `assets/`
and `content/` relative to the working directory).

## Content

Project and article content lives in `content/`, as portable JSON metadata
plus a Markdown body. **Adding a project needs no Haskell changes.**

```text
content/
  projects/
    brigid/                 directory name = slug = URL (/work/brigid/)
      project.json          metadata (below)
      body.md               the narrative (Markdown)
      card.svg              media referenced by project.json or body.md
  writing/
    {slug}/                 the same, for articles (/writing/{slug}/)
      article.json
      body.md
```

**Discovery.** Entries are discovered in sorted order, and dot-files are
ignored. Every entry must be a real directory (not a symlink) named by a
valid slug: lowercase ASCII letters and digits in hyphen-separated words.
The metadata's `slug` must equal the directory name. Content slugs only
ever appear under `/work/` or `/writing/`, so content cannot claim
`/about/`, `/404.html` or any other fixed route.

### Adding a project

1. Create `content/projects/{slug}/` with a `project.json` and a Markdown
   body.
2. Put any images it uses in the same directory (subdirectories are fine).
3. Run `site check`. Every problem is reported with its file, field and
   Markdown line.
4. Set `"publication_status": "published"` when it is ready, and build.

### `project.json` fields

Unknown or misspelled fields are errors, and `null` is not a way to omit a
field: leave it out.

| Field | Required | Meaning |
| --- | --- | --- |
| `slug` | yes | Must equal the directory name |
| `title` | yes | Non-empty text |
| `summary` | yes | One sentence. Used on the card, as the page subtitle and as the meta description. No straight `"` (see the security policy) |
| `category` | yes | What it is, e.g. `"Haskell library"`. Shown with the development status: "Haskell library · In development" |
| `development_status` | yes | `implemented`, `in_development` or `proposed`, shown as "Implemented", "In development" or "Proposed". It describes the work and **never** controls publication |
| `publication_status` | yes | `draft` or `published`. Only `published` content gets a route, card, link or media file |
| `technologies` | yes | A list of text, shown as tags |
| `featured_order` | no | 1–10000, unique among published projects. Featured projects appear in this order in the homepage's Selected Work, and first in the Work index. Default: not featured (Work index only, after featured projects, by title then slug) |
| `links` | no | `[{ "label": "…", "url": "https://…" }]`, shown under the project title. `https://` only. Default `[]` |
| `body` | yes | Path of the Markdown body (`.md`) inside the project directory |
| `showcase` | no | Project evidence (below). Default: none, giving a text-only card and no figure |

**Showcase kinds.** The `kind` field selects one of these:

- `"image"`, with `src` and `alt`;
- `"video"`, with `src`, optional `poster`, and `transcript`;
- `"audio"`, with `src` and `transcript`;
- `"code"`, with `src` and `caption`;
- `"interactive"`, with `app`.

Phase 02 renders `image` only. On the card it is decorative; on the project
page it is a figure with its alt text. A **published** project using another
kind fails validation; that presentation is Phase 04. `interactive` only
accepts application identifiers the site implements, and there are none yet.

### `article.json` fields

The fields are `slug`, `title`, `summary`, `publication_status` and `body`,
all as above. `date` is optional, in the form `YYYY-MM-DD`; articles are
listed newest first, undated last. A Writing index and the navigation's
"Writing" link appear only when at least one article is published. No empty
Writing page is ever generated.

### Drafts

Draft projects and articles are still **fully validated**, so mistakes
surface early, except that a draft may use showcase kinds not yet rendered.
They produce **nothing** in `dist/`:

- no page;
- no card;
- no navigation entry;
- no link;
- no media file.

Markdown and JSON sources are never copied into the output.

### Markdown

The parser is CommonMark, via `commonmark-hs`. These features are
supported:

- paragraphs;
- `##` to `####` headings;
- `*emphasis*` and `**strong**`;
- links;
- images;
- `` `inline code` ``;
- fenced code blocks, with an optional language;
- bullet and ordered lists, nested;
- block quotes;
- horizontal rules;
- backslash escapes and HTML entities, which become plain text.

Tables are not supported.

**Headings.** The page owns the `<h1>`, so a body uses `##` and below:

- `#` is an error;
- the first heading must be `##`, and levels may not be skipped;
- headings must be at the top level (not in lists or quotes);
- `#####` and deeper are errors.

Each `##` starts a section and an entry in the project sidebar. Text before
the first `##` becomes an unlisted lead.

**Heading ids.** Ids are derived from the heading text:

- letters and digits (any script) are kept, lowercased;
- everything else becomes single hyphens;
- if nothing is left, the id is `section`.

Repeats, and ids the page already uses, get `-2`, `-3` and so on. The
sidebar links to exactly these ids.

**Code.** Code is escaped text, readable without JavaScript, with no
syntax highlighting. Long lines scroll inside the block, never the page.

**Images.** Write `![alt text](diagram.svg)`. The path is relative to the
content item's directory, and must name an image file there:

- the allowed types are `.svg`, `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`
  and `.avif`;
- alt text is required;
- the image is published to `/media/projects/{slug}/…` or
  `/media/writing/{slug}/…`.

### Markdown HTML and URL security policy

Markdown is content, not trusted HTML.

- **Raw HTML is rejected**, inline or block, with its line number. There is
  no sanitizer.
- **Links** may only be:
  - `https://host/…`;
  - a root-absolute site path `/…`, which must resolve to a generated page
    or file (checked by the build);
  - a `#fragment`, which must name an id on the page.

  Everything else is rejected: other schemes (`javascript:`, `data:`,
  `vbscript:`, `http:`), protocol-relative `//`, relative paths, and any
  destination containing whitespace, control characters, quotes, `<`, `>`,
  backslashes or backticks. Destinations are checked after the parser
  decodes entities and escapes, so `&#106;avascript:` is caught as
  `javascript:`. Link titles are dropped.
- **Links inside emphasis or headings are rejected.** Brigid does not allow
  `<a>` there. Formatting inside link text is rendered as plain text, and
  images inside links are rejected.
- **Images** may only reference media inside the content item's own
  directory. Remote images, traversal (`..`), absolute paths, symlinks that
  escape, and non-image files such as `body.md` or `project.json` are all
  rejected.
- **Straight double quotes are rejected** in text that becomes an HTML
  attribute: summaries and alt text. Brigid, at the pinned commit, does not
  escape `"` inside attribute values. Use typographic quotes (“ ”). Text
  content is escaped normally.
- **Defence in depth.** Every generated page is scanned before publishing:
  - every real tag (Brigid escapes `<` in text) is checked;
  - the build fails on any `on…=` event-handler attribute;
  - the build also fails on any `<script>`, `<iframe>`, `<object>`,
    `<embed>`, `<style>`, `<base>` or frame element.

  See [`docs/adr/0001-content-pipeline.md`](docs/adr/0001-content-pipeline.md).

## Development workflow

### Rebuild-and-preview loop

Leave the preview running (`docker compose up -d preview`). After an edit,
run `docker compose run --rm site-build` and reload the browser. A warm
rebuild takes a few seconds. The preview serves the new files at once,
because the build replaces the contents of `dist/`, never the directory
itself.

If [`watchexec`](https://github.com/watchexec/watchexec) is installed on the
host, it can automate the loop. No custom watcher is part of the project:

```sh
watchexec -w src -w app -w assets -- docker compose run --rm site-build
```

### Removing generated output

`dist/`, `dist.tmp/` and `dist.old/` are generated and git-ignored.

- **To remove output:** stop the preview first, so its bind mount is not
  left dangling, then delete. Run `docker compose stop preview`, then
  `rm -rf dist dist.tmp`. The next build recreates `dist/`.
- **Output from before the ownership marker:** a `dist/` built before the
  marker existed is refused (`no .personal-site-output marker`). Remove it
  once, as above, and rebuild.
- **`dist.old/`:** this exists only if a build was interrupted while
  publishing, and it may hold the last good output. The build refuses to
  run while it exists. Inspect it, then delete it.
- **Caches:** `docker compose down -v` deletes the Stack cache volume. The
  next build is cold again (about 7.5 minutes).

## Routes and output files

URLs and output files are both derived from one function,
`Site.Routes.routePath`:

| Route | URL | Output |
| --- | --- | --- |
| `Home` | `/` | `dist/index.html` |
| `WorkIndex` | `/work/` | `dist/work/index.html` |
| `WorkDetail slug` | `/work/{slug}/` | `dist/work/{slug}/index.html` (one per published project; today `brigid`) |
| `WritingIndex` | `/writing/` | `dist/writing/index.html` (only if published writing exists) |
| `WritingArticle slug` | `/writing/{slug}/` | `dist/writing/{slug}/index.html` (one per published article) |
| `About` | `/about/` | `dist/about/index.html` |
| `NotFound` | `/404.html` | `dist/404.html` |
| assets | `/assets/<path>` | `dist/assets/<path>` (22 files, listed in `Site.Assets.allAssets`) |
| content media | `/media/projects/{slug}/<path>`, `/media/writing/{slug}/<path>` | the same under `dist/` (published items only) |

**All URLs are root-absolute.** The same markup works at any depth, and in
`404.html`, which a static host serves at arbitrary missing paths. This
means the site must be served from the root of its origin. A sub-path
deployment would need a base-URL setting, which is not implemented.

**Slugs** (`WorkDetail`) are validated by `mkSlug`:
- lowercase ASCII letters and digits in hyphen-separated words;
- at most 64 characters.

Anything else is rejected rather than normalised, including uppercase,
Unicode, dots, slashes and doubled or trailing hyphens. So two spellings can
never map to one URL or file.

## Architecture

```text
content/projects/*, content/writing/*
        │
        ▼
Site.Content.Load               discover (sorted); strict JSON → typed metadata; Markdown
        │                       → Site.Content.Markdown (parse + validate); every file read
        │                       through Site.Source (no traversal, no symlink escape)
        ▼
Site.Definition.siteFrom        publication filter: published projects/articles → pages,
        │                       cards, nav, media; plus the fixed pages and allAssets
        ▼
Site.Manifest.mkManifest        route / asset / media → OutputPath (pure); rejects invalid
        │                       paths, case-insensitive collisions, file/dir conflicts
        ▼
Site.Build.checkSite            assets and media re-checked (Site.Source); stylesheet url()s
        │                       are listed assets; pages rendered in memory (Brigid, with
        │                       Markdown via Site.Content.Render) and validated
        │                       (Site.Validate): one <h1>, landmarks, unique ids, no active
        │                       content, every internal href/src and #fragment resolves
        ▼
Site.Build.buildSite            refuse unsafe --out (ownership marker); write DIR.tmp/;
                                staged files must equal the manifest exactly; promote
                                into DIR with rollback
```

| Module | Role |
| --- | --- |
| `Site.Path` | `OutputPath`: a validated, canonical, root-relative output path |
| `Site.Source` | The single source-file check: exists, regular file, resolves inside its root |
| `Site.Routes` | `Slug`, `Route`, and the route → URL → output mapping; fragment ids |
| `Site.Assets` | The explicit asset manifest and asset URLs |
| `Site.Content.Types` | Typed content: `Project`, `Article`, statuses, `Showcase`, media, ordering and publication filters |
| `Site.Content.Load` | Discovery, strict JSON decoding (all errors reported), file and media checks |
| `Site.Content.Markdown` | CommonMark parsing into our own syntax tree; the URL, raw-HTML, heading and id policies |
| `Site.Content.Render` | The Markdown → Brigid boundary (typed elements only, no HTML strings) |
| `Site.Page` | `SiteConfig`, `Page` (route, title, description, layout, `<main>` content), `Site` |
| `Site.Layout` | The shared Brigid shell: document, head, navigation, footer |
| `Site.Components` | Shared pieces: decorative images, ruled headings, the project card |
| `Site.Pages.{Home,Work,Writing,About,NotFound}` | One module per page family. Work holds the index and the shared project-page layout: a sidebar (All projects, current project, one link per Markdown `##` section) beside the content, after `design/references/project-render-03.jpg`. Home holds the homepage introduction as one named constant |
| `Site.Definition` | The site derived from content: publication filtering and the page list |
| `Site.Manifest` | The output manifest and its collision checks |
| `Site.Validate` | Checks on rendered HTML (structure, ids, active content, internal links) |
| `Site.Build` | `loadSite`, `checkSite`, `buildSite`, staging and promotion |

### Publishing and filesystem assumptions

- `DIR.tmp/` (staging) and `DIR.old/` (backup) are **siblings** of `DIR`.
  They are on the same filesystem, so each move is a `rename(2)`.
- Promotion works in three steps:
  1. Move `DIR`'s current children into `DIR.old/`.
  2. Move the staged children into `DIR`.
  3. Delete `DIR.old/`.
- **If any move fails,** the build removes the new entries, moves the old
  ones back, and reports the failure. If that rollback also fails, the
  error names `DIR.old/` as holding the previous output.
- **Atomicity:** each rename is atomic. The swap as a whole is not, so a
  request during the few milliseconds of the swap may see a mix. For a
  local build and preview, that is acceptable.
- **`DIR` itself is never replaced,** only its children. The preview
  container bind-mounts `dist/`, and that mount stays valid.
- **Output ownership.** Every build writes one extra file at the root of
  the output, `.personal-site-output`, with fixed contents. An existing
  non-empty directory is replaced **only** if that marker is present as a
  regular file (not a symlink, not a directory) with exactly those bytes.
  - A missing or empty directory is always accepted.
  - A foreign directory is refused even if it contains `index.html`, and
    so is one with a missing, malformed or symlinked marker.
  - The marker is the only non-page, non-asset file in the output. The
    Phase 07 deploy must exclude it.
- **The build also refuses an `--out` that could destroy sources:**
  - the source tree or any directory containing it;
  - anything inside `assets/`;
  - an existing file.

### Adding a fixed (non-content) page

Projects and articles need no code (see Content). For a new fixed page:

1. Add a constructor to `Route` in `src/Site/Routes.hs` and its URL in
   `routePath`. The output file follows automatically.
2. Write `src/Site/Pages/<Name>.hs` exporting `page :: SiteConfig -> Page`.
   Put exactly one `<h1>` in `pageMain`; `pageHeading` gives the house
   style. Use `Interior` layout.
3. List the page in `Site.Definition.siteFrom`. No package edits are needed:
   hpack discovers the new module.
4. Link to it with `routeUrl YourRoute`, never a string. Add it to
   `Site.Layout.navItems` only if it belongs in the primary navigation.
5. Run `site check`, then the tests. The validator fails the build if the
   new page collides with another output, links to anything not generated,
   or lacks a single `<h1>`.

New assets go in `assets/` and in `Site.Assets.allAssets`. Pages refer to
them with `assetUrl`.

### Diagnosing failures

Every failure prints `Build failed: …` and names the offending route, asset
or file. The previous output is left untouched.

| Message | Meaning and fix |
| --- | --- |
| `invalid content:` then `content/projects/x/project.json:` and field messages | Fix the named fields. Every independent problem in every file is listed |
| `field "development_status": invalid value "…"; expected one of: …` | Use one of the listed values |
| `unknown field "…"` / `missing required field "…"` | Misspelled or missing metadata (see Content) |
| `field "body": referenced file "…" does not exist` | The Markdown body named in the metadata is missing |
| `content/projects/x/body.md:` then `line N: …` | A Markdown problem at that line: raw HTML, a disallowed link, a heading-level problem, or an image without alt text |
| `… resolves to …, outside its permitted directory (symlink escape)` | A content file or media file is a symlink out of its directory |
| `must not contain a straight double quote` | Use typographic quotes in summaries and alt text |
| `page /… contains active content in the tag …` | A value broke out of its attribute. This should be impossible. Report it, as it indicates an escaping gap |
| `required asset(s) missing from the source tree: - assets/images/x.webp` | A file in `allAssets` does not exist. Restore it, or remove it from the list |
| `assets/x is not a regular file` / `resolves to …, outside the assets directory` | The asset is a directory, or a symlink pointing out of `assets/`. Replace it with a real file |
| `assets/styles/site.css references "../images/x.png", which is not a listed asset` | Add the file to `allAssets`, or fix the `url()` |
| `output collision: page / -> index.html, page / -> index.html …` | Two pages share a route, or two outputs differ only in letter case. Remove or rename one |
| `output conflict: … is a file, but … needs it to be a directory` | One output's path is a directory prefix of another's |
| `asset assets/../x has an invalid path: … unsafe segment ".."` | Asset paths must be plain relative paths under `assets/` |
| `invalid slug "Brigid": …` | Use a lowercase, hyphenated ASCII slug |
| `page /about/ links to "/work/missing/": work/missing/index.html is not generated` | Fix the link, or add the page. Use `routeUrl`, not literal strings |
| `page /x/ links to "/about/#y": no element with id "y" on /about/` | The fragment target id does not exist on that page |
| `page /x/ must have exactly one <h1>, found 2` | Fix the page's heading structure |
| `refusing to write to "…": it is not empty and is not a directory this generator manages (…)` | The directory has no valid ownership marker. Use a new or empty directory, or remove this one yourself after checking its contents |
| `refusing to write to "…": it contains the source tree` (or `inside the assets directory`, `it is a file`) | The `--out` directory is unsafe (see above) |
| `"dist.old" exists, so an earlier build was interrupted while publishing` | Inspect `dist.old/` (it may hold the last good output), delete it, and rebuild |

## What happens on a clean checkout

1. **Build the image.** `docker compose build site-build` pulls the pinned
   base image and installs the two system libraries Brigid needs. The image
   contains no project source; the repository is bind-mounted at `/work` at
   run time.
2. **Cold build.** The first `docker compose run --rm site-build` creates the
   `stack-root` named volume and compiles the full dependency graph, Brigid
   included. This took about 7.5 minutes on an Apple-silicon laptop.
3. **Warm builds.** Later runs reuse the volume (and `.stack-work/` in the
   working tree) and take seconds. `docker compose down -v` deletes the
   cache volume.

The `preview` service is plain nginx serving `dist/` read-only. Its config,
[`docker/preview.conf`](docker/preview.conf), answers missing paths with
`404.html` and HTTP 404, as a static host does. It has no Haskell and no
backend, and it refuses to start if `dist/` does not exist yet.

### Inspecting the toolchain

```sh
docker compose run --rm site-build ghc --version     # 9.10.3
docker compose run --rm site-build stack --version   # 3.7.1
docker compose run --rm site-build stack ls dependencies
```

### File ownership

The container entrypoint ([`docker/entrypoint.sh`](docker/entrypoint.sh))
runs every command as the UID/GID that owns the bind-mounted repository. So
`dist/` and `.stack-work/` belong to the host user on Linux, with no `sudo` or
`chown` needed on the host.

- **Named volume:** a fresh one is root-owned, so the entrypoint hands the
  volume's top directory to that user.
- **Docker Desktop (macOS/Windows):** the VM translates ownership, so files
  land as the host user either way.

## Hero and emblem artwork

The hero plates (`assets/images/hero-plate-{left,centre,right}.webp`) are
reconstructed from the owner's approved render. The About emblem
(`about-tree.webp`) is taken from the branding board.

- **Reconstruction:** [`reconstruct.py`](tools/art/reconstruct.py) inpaints
  out all text and UI and cuts the plates.
- **Not reproducible from the repository:** the art scripts read the
  full-resolution originals from the git-ignored reference kit in `.local/`.
- **Committed outputs:** the generated images are committed source assets.
  The site build only copies them and never runs these scripts, so it stays
  deterministic.

```sh
# development-only art tooling (same tools image); outputs are committed
docker compose --profile tools run --rm art python3 tools/art/reconstruct.py     # hero plates from the render
docker compose --profile tools run --rm art python3 tools/art/emblem.py          # About tree emblem
docker compose --profile tools run --rm art python3 tools/art/compare.py         # registered render vs proof
docker compose --profile tools run --rm art python3 tools/art/monogram_sheet.py  # monogram sheet
```
