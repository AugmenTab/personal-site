# personal-site

A personal technical folio: a static site generated by a small Haskell
executable that renders HTML with [Brigid](https://github.com/AugmenTab/brigid).
The visual language is dark Art Deco noir after the *Eclipsing Eden* brand.

**Current state: Phase 07 (release engineering for Cloudflare Workers
Static Assets) is implemented and tested locally, but nothing is deployed.
Phase 06 (accessibility, performance and visual QA) is complete; Phase 05
is merged.** Publication waits for the owner's review and an explicit
`scripts/release.sh deploy --confirm` (see
[`docs/operations/deployment.md`](docs/operations/deployment.md)). The
symbolic hero artwork
for Black and Brigid has still not been delivered (see
[Hero artwork](#hero-artwork)).
Pages are generated through one shared Brigid shell (navigation, footer,
canonical and social metadata):

- the homepage: the approved Phase 00 arrival, then Selected Work,
  Engineering Philosophy, a conditional Writing preview, and Contact (see
  [Homepage](#homepage));
- a Work index: a two-column card grid with search and category filters
  that work without a server, and a complete list without JavaScript (see
  [Search and filtering](#search-and-filtering));
- one dossier per published project, loaded from `content/projects/` (JSON
  metadata and a Markdown body, presented in five typed section layouts;
  see [Project dossiers](#project-dossiers)): Black, Brigid and Paranoia Engine;
- an About page: the personal profile, with the tree-and-eclipse emblem;
- a 404 document;
- a Writing index at `/writing/`, always published. Until an article is
  published (none is yet) it says "Coming soon." and lists nothing. Each
  published article gets its own page, and the homepage Writing preview
  appears only once one exists;
- a résumé PDF at `/resume.pdf`, published only when `content/resume.pdf`
  exists (none does yet);
- `/sitemap.xml` and `/robots.txt`, generated from the published routes
  (see [Metadata and discovery](#metadata-and-discovery)).

Phase retrospectives are kept locally in `.local/retros/phase-NN.md`
(git-ignored). The committed evidence is in [`design/proof/`](design/proof/).
The Phase 00 gate report is [`DESIGN_GATE.md`](DESIGN_GATE.md), and
the approved visual baseline is in [`design/regression/`](design/regression/).
Design decisions are recorded in [`docs/adr/`](docs/adr/).

## Requirements

Docker Engine and Docker Compose v2. Nothing else: GHC, Stack, Cabal and all
Haskell dependencies live in the container. Screenshot tooling also runs in a
container.


`site-build` runs [`docker/build-site.sh`](docker/build-site.sh), i.e.
`stack build` followed by `stack exec -- site build --out dist`.

### The `site` CLI

| Command | Effect | Exit status |
| --- | --- | --- |
| `site build [--root SRC] [--out DIR]` | Validate everything, render into `DIR.tmp/`, verify, then publish into `DIR` (default `dist`) | 0 on success; 1 with a `Build failed: …` message, leaving `DIR` untouched |
| `site check [--root SRC]` | The same validation as `build` (content, routes, output paths, assets, media, stylesheets, rendered pages and links). Prints the output manifest and writes nothing | 0 if valid, 1 otherwise |
| `site manifest [--root SRC]` | The same validation as `check`, then only the published output paths, one per line, and nothing else on standard output. This is the release allowlist (Phase 07). The ownership marker is never listed | 0 if valid, 1 otherwise |

Run it inside the container, from the repository root. It reads `assets/`
and `content/` from `SRC`, which defaults to the working directory; another
root is only for development previews ([Previewing a hero](#previewing-a-hero)).
Content warnings, such as a hero over its size budget, are printed to
standard error as `warning: …` lines and do not fail the command.

## Content

Project and article content lives in `content/`, as portable JSON metadata
plus a Markdown body. **Adding a project needs no Haskell changes.**

```text
content/
  projects/
    brigid/                 directory name = slug = URL (/work/brigid/)
      project.json          metadata (below)
      body.md               the narrative (Markdown)
      card.svg              media referenced by project.json or body.md
  writing/
    {slug}/                 the same, for articles (/writing/{slug}/)
      article.json
      body.md
```

**Discovery.** Entries are discovered in sorted order, and dot-files are
ignored. Every entry must be a real directory (not a symlink) named by a
valid slug: lowercase ASCII letters and digits in hyphen-separated words.
The metadata's `slug` must equal the directory name. Content slugs only
ever appear under `/work/` or `/writing/`, so content cannot claim
`/about/`, `/404.html` or any other fixed route.

### Adding a project

1. Create `content/projects/{slug}/` with a `project.json` and a Markdown
   body.
2. Put any images it uses in the same directory (subdirectories are fine).
3. Run `site check`. Every problem is reported with its file, field and
   Markdown line.
4. Set `"publication_status": "published"` when it is ready, and build.

### `project.json` fields

Unknown or misspelled fields are errors, and `null` is not a way to omit a
field: leave it out.

| Field | Required | Meaning |
| --- | --- | --- |
| `slug` | yes | Must equal the directory name |
| `title` | yes | Non-empty text |
| `summary` | yes | One sentence. Used on the card, as the page subtitle and as the meta description. No straight `"` (see the security policy) |
| `category` | yes | The primary classification: one category id from the [taxonomy](#taxonomy), e.g. `"libraries-tooling"`. Shown by its label with the development status ("Libraries & Tooling · In development") and used by the Work index's filter chips |
| `topics` | no | Up to five topic ids from the [taxonomy](#taxonomy), e.g. `["type-systems"]`: subjects that cut across categories. Shown on the dossier and searchable. Each at most once; displayed in vocabulary order. Default `[]` |
| `development_status` | yes | `implemented`, `in_development` or `proposed`, shown as "Implemented", "In development" or "Proposed". It describes the work and **never** controls publication |
| `publication_status` | yes | `draft` or `published`. Only `published` content gets a route, card, link, media file or sitemap entry |
| `technologies` | yes | Concrete languages, frameworks and tools as text (`["Haskell", "LLVM IR"]`), shown as tags and searchable. Each at most once, ignoring case; a topic or category here is an error (move it to its own field) |
| `featured_order` | no | 1–10000, unique among published projects. Featured projects appear in this order in the homepage's Selected Work, and first in the Work index. Default: not featured (Work index only, after featured projects, by title then slug) |
| `links` | no | `[{ "label": "…", "url": "https://…" }]`, shown under the project title. `https://` only. Default `[]` |
| `body` | yes | Path of the Markdown body (`.md`) inside the project directory. Each `##` heading starts a dossier section |
| `showcase` | no | The card art (below), shown on the project's cards only. Default: none, giving a text-only card |
| `hero` | no | The symbolic hero artwork, with its alt policy and focus points (see [Hero artwork](#hero-artwork)). Default: none, giving the plain header beside the sidebar |
| `sections` | no | How each `##` section is presented: an object from section id to layout (see [Project dossiers](#project-dossiers)). Sections not listed use the `overview` layout |

**Showcase kinds.** The `kind` field selects one of these:

- `"image"`, with `src` and `alt`;
- `"video"`, with `src`, optional `poster`, and `transcript`;
- `"audio"`, with `src` and `transcript`;
- `"code"`, with `src` and `caption`;
- `"interactive"`, with `app`.

The site renders `image` only, as decorative art on the project's cards
(homepage and Work index). Since Phase 05 the dossier never shows it: a
project page without a hero opens with its header (title, summary,
technologies, topics, links) and goes straight into its sections, with no
stand-in figure. Evidence (diagrams, screenshots, code) belongs in a
section artifact, not here. A **published** project using another kind
fails validation; drafts may use them. `interactive` only accepts
application identifiers the site implements, and there are none yet.

### Taxonomy

Categories and topics are a small controlled vocabulary, defined once in
[`src/Site/Taxonomy.hs`](src/Site/Taxonomy.hs). `project.json` names them
by id; the labels come from the vocabulary, so a card, the filters, the
search data and the dossier always use the same words. There are no
hierarchies or synonyms.

| Category id | Label |
| --- | --- |
| `programming-languages` | Programming Languages |
| `libraries-tooling` | Libraries & Tooling |
| `ai-automation` | AI & Automation |
| `simulation-games` | Simulation & Games |
| `creative-technology` | Creative Technology |

| Topic id | Label |
| --- | --- |
| `type-systems` | Type Systems |
| `compiler-engineering` | Compiler Engineering |
| `formal-verification` | Formal Verification |
| `web-development` | Web Development |
| `ai-agents` | AI Agents |
| `deterministic-simulation` | Deterministic Simulation |
| `game-engines` | Game Engines |
| `audio-engineering` | Audio Engineering |

- **Setting a category:** `"category": "simulation-games"`. Every project
  has exactly one. Free text (the pre-Phase 05 form, e.g. `"Haskell
  library"`) fails with the list of valid ids.
- **Adding topics:** `"topics": ["deterministic-simulation",
  "game-engines"]`. Tag only what the project's own dossier supports.
- **Extending the vocabulary:** add a constructor, its id and its label in
  `Site.Taxonomy` (and a row above). Unused entries are fine; chips appear
  only for categories that a published project uses.
- **Technologies** stay free text, but a duplicate (ignoring case) or a
  topic or category label in the list is an error.

The real projects: Black is Programming Languages (Type Systems, Compiler
Engineering, Formal Verification); Brigid is Libraries & Tooling (Type
Systems, Web Development); Paranoia Engine is Simulation & Games (Deterministic
Simulation, Game Engines). "Type systems", "Verification", "Type safety"
and "Deterministic simulation" moved out of `technologies` into topics.

### Search and filtering

The Work index lists every published project as a card, in a two-column
grid from 1100px wide and one column below. Above the grid are a search
field, one filter chip per category in use (after **All**), and a live
result count.

- **Matching.** A project is shown when it is in the selected category
  (All: any) **and** its text contains every word of the query, in any
  order. Case and extra whitespace are ignored. The text is the project's
  title, summary, category label, technologies and topic labels, the same
  record the card and dossier render, written into the item's
  `data-search` attribute by the generator. There is no separate search
  index.
- **Empty results** show "No projects match this search." and a **Show
  all projects** button, which clears both filters and returns focus to
  the search field.
- **Without JavaScript** every card is in the HTML and visible, and the
  controls are `hidden`, so no inert control is shown.
- **The script** is [`assets/scripts/work-filter.js`](assets/scripts/work-filter.js),
  a small vanilla module loaded only on `/work/`. It fetches and stores
  nothing. It is the only script on the site: the build's active-content
  scan allows exactly `<script type="module" src="/assets/scripts/NAME.js">`
  with no inline code, and the link checker requires the file to be a
  listed asset.
- **Accessibility.** The field has a visible label; chips are buttons with
  `aria-pressed` (the selected one also carries a diamond, so the state is
  not colour alone); the count is a polite live region; if a filter hides
  the card that has keyboard focus, focus returns to the search field.

To test it: build, `docker compose up -d preview`, open
<http://localhost:8080/work/> and type (e.g. `haskell`, `type systems`,
`replayable`), or run the screenshot suite, which exercises names,
descriptions, topics, chips, combined filters, the empty state, reset, the
keyboard and the no-JavaScript page (`design/proof/phase-05/work/`).

## Project dossiers

A project page is a dossier: the shared shell (navigation, project sidebar,
typography, palette, frames), an opening (an optional symbolic **hero**, or
the plain header), and the body's sections (see [Page layout](#page-layout)). The page system is shared; each project's identity comes
from its hero and from the mix of layouts its sections use.

### Section layouts

There are exactly five layouts. Each `##` section of the body is one
section of the dossier, in body order, with the id derived from its
heading (see [Markdown](#markdown)). `sections` in `project.json` gives a
section its layout; a section not listed is an `overview`.

```json
"sections": {
  "overview":         { "layout": "overview", "facts": [ { "label": "Licence", "value": "BSD-3-Clause" } ] },
  "the-pipeline":     { "layout": "wide-exhibit", "artifact": { "kind": "diagram", "src": "pipeline.svg", "alt": "…" } },
  "an-example":       { "layout": "split", "artifact_side": "start",
                        "artifact": { "kind": "code", "src": "examples/Example.hs", "label": "Example.hs", "language": "haskell" } },
  "design-goals":     { "layout": "grid" },
  "resources":        { "layout": "resources", "sidebar": true }
}
```

| Layout | Use for | Presents | Fields |
| --- | --- | --- | --- |
| `overview` | Overview, motivation, framing, plain prose | The section's prose, then an optional cluster of facts | `facts`: `[{ "label", "value" }]` (optional) |
| `wide-exhibit` | An architecture figure, a large code artifact, a showpiece | The artifact at full column width, then the prose as its caption | `artifact` (required) |
| `split` | Code and explanation, figure and explanation | Prose beside the artifact; stacked below 1180px, in reading order | `artifact` (required), `artifact_side`: `"end"` (default) or `"start"` |
| `grid` | Features, principles, guarantees at a glance | An optional introduction, then a lattice of short items | none; the Markdown is the content (below) |
| `resources` | Status, limitations, links, references | A quiet closing strip | none |

Every entry also takes `sidebar` (default `true`): `false` keeps the
section on the page but out of the sidebar. The sidebar always lists the
real sections that are on the page, in order, and nothing else.

**Validation.** Every rule is checked, and each problem is reported with
its file:

- a `sections` key must be the id of a `##` section of the body (the error
  lists the real ids);
- the layout must be one of the five, and each layout accepts only its own
  fields;
- `resources` sections close the dossier: no other layout may follow one;
- an artifact's file must exist inside the project directory.

**Grids** are written in Markdown, so the prose stays in one file. A grid
section is optional introductory paragraphs, then exactly one bullet list
of 2 to 9 items, each a single paragraph starting with a bold title:

```markdown
## Design principles

These are the rules the compiler enforces today.

- **Proved, not assumed.** An integer result must provably fit its type.
- **Closed by default.** Records and variants are closed.
```

A trailing full stop on the title is dropped in the grid. Anything after
the list is an error.

**Artifacts.** The evidence a section shows beside or above its prose:

| `kind` | Fields | Presentation |
| --- | --- | --- |
| `image` | `src`, `alt` | A framed image scaled to the column. Published as media |
| `diagram` | `src`, `alt` | A framed image that keeps a legible width on phones (it scrolls inside its frame, never the page) and links to the full-size file. Published as media |
| `code` | `src`, `label`, `language` (optional) | A code panel with the label on its tab. The file is read at build time (UTF-8, at most 32 KiB) and shown as escaped text; it is **not** published. Long lines wrap with a hanging indent |

Use `code` artifacts for code that must stay exact: the Black programs are
verbatim from its conformance suite, and the Brigid excerpt is verbatim
from `src/Site/Pages/Work.hs` (a test fails if either drifts). There is no
syntax highlighting yet; code is readable without JavaScript.

**Not supported, by design:** arbitrary HTML, author-defined layouts, video
or audio artifacts (no published project needs them yet), and live demos.
A new layout is a code change to the typed model in
`Site.Content.Types`, not a content convention.

### Page layout

Every project page has the same structure, after the approved project
render. A hero only changes what opens the main column:

```text
global navigation
article.project.project-layout
  ├── opening       header.project-hero (artwork + real header text)
  │                 or div.project__header (no hero)
  ├── sidebar       nav.project-nav: All projects, the project, its sections
  │                 (and the compact "On this page" index for narrow screens)
  └── dossier       div.project__body: lead, sections
```

- **Desktop (above 900px):** two columns. The sidebar starts directly under
  the global navigation, beside the opening, and stays in view (sticky)
  beside the dossier. The hero is confined to the main column, the same
  width as the dossier.
- **Tablet and phone (900px and below, Phase 05):** one column, in source
  order: the opening (which carries the title), then **← All projects** and
  a collapsed **On this page** disclosure (native `<details>`, no
  JavaScript) listing the sections, then the dossier. The gilded
  current-project tab is not repeated there. Both section lists are
  rendered from the same `sidebarSections` value, so they cannot drift;
  CSS displays exactly one, so the keyboard and screen readers meet one
  index. Source order is also reading and keyboard order at every width.
  Section links are plain anchors.
- **Phones (640px and below):** the hero runs edge to edge, taller than
  wide, cropped at its mobile focus point.

### Hero artwork

A hero is the atmospheric opening of the dossier's main column: symbolic,
painterly artwork in the site's world (noir, antique gold, architectural or
ceremonial geometry), never a screenshot, diagram or code. It is shallow
and cinematic (about 46% of the viewport height on desktop, within 20–28rem),
so the first section starts within the first desktop screen. The artwork
has no frame: its edges fade into the page, and it is darkened behind the
title, summary, tags and links, which are real HTML over it. The art never
contains text.

```json
"hero": {
  "src": "hero.webp",
  "alt": "A gothic window seen from below, opening onto a night sky",
  "focus": { "desktop": { "x": 70, "y": 35 }, "mobile": { "x": 80, "y": 45 } }
}
```

| Field | Meaning |
| --- | --- |
| `src` | An image inside the project directory. See the size policy below |
| `alt` *or* `decorative` | The alt text policy, stated explicitly. `alt` describes the artwork; `"decorative": true` gives empty alt text and hides it from assistive technology. Exactly one is required |
| `focus` | Which point of the artwork stays in view when the hero crops it (below). Default: the centre |

**Focus.** `x` is measured from the artwork's left edge and `y` from its
top, in percent: whole numbers from 0 to 100 in steps of 5. The point x% of
the way across the artwork is placed x% of the way across the hero (CSS
`object-position`), so `{ "x": 80, "y": 30 }` keeps an upper-right subject
in view. `focus` takes one of three forms:

| Form | Meaning |
| --- | --- |
| `{ "desktop": {…}, "mobile": {…} }` | Separate points. `desktop` applies above 640px, `mobile` at 640px and below (phones, where the hero is taller than wide). Omitted `desktop`: the centre. Omitted `mobile`: the desktop point |
| `{ "x": 65, "y": 35 }` | One point at every width |
| `"center"`, `"top"`, `"bottom"` | **Phase 04 keywords, still accepted:** `(50, 50)`, `(50, 10)` and `(50, 90)` at every width |

An omitted `x` or `y` is 50. Out-of-range, fractional, non-numeric and
off-step values, unknown keys and empty points are errors naming the field,
e.g. `field "focus": field "desktop": field "x": must be a multiple of 5 (e.g.
60 or 65), got 62`. Each value becomes a fixed class
(`project-hero--x-65`, `--y-35`, `--mx-80`, `--my-45`) defined in the
stylesheet, so no CSS text ever comes from content.

The crop switches between the two points at 640px only, the same width at
which the hero itself changes shape, so there is no other jump. Compose
art with the subject toward one side and dark negative space where the
text sits (the lower left on desktop, the lower part on phones).

**Size policy.** The hero is the page's largest image and is fetched
eagerly, so size matters, but painterly art must not be crushed to meet a
number. The policy is `defaultHeroSizePolicy` in `Site.Content.Load`:

| Size | Result |
| --- | --- |
| up to 1 MiB (the **budget**) | Accepted silently. This is the optimization target |
| over 1 MiB, up to 8 MiB (the **ceiling**) | Accepted. `site check` and `site build` print a `warning:` line with the file, its size, the budget and the ceiling |
| over 8 MiB | The build fails, naming the size, ceiling and budget |

Rationale: 1 MiB keeps a 2400px painterly WebP fast on a typical
connection. Past that, the warning makes the cost visible at review time
rather than forbidding it. 8 MiB stops an unoptimized PNG or a mistake
from reaching production unnoticed. To change the policy, edit
`defaultHeroSizePolicy`; `tools/art/promote_hero.py` mirrors both numbers.

**Workflow.** Heroes are prepared outside the repository and staged in
`.local/heroes/{slug}-hero.png` (git-ignored; keep the original there).

1. Preview it first, without touching `content/` (next section).
2. Promote it:

   ```sh
   docker compose --profile tools run --rm art python3 tools/art/promote_hero.py black
   ```

   This writes `content/projects/black/hero.webp`, scaled down to at most
   2400px wide (never further to meet the budget), in sRGB with no
   metadata. WebP quality starts at 90 and steps down to no lower than 80
   until the file fits the budget. If it still does not fit, it is kept at
   80 with a note, and the build will warn. The tool never crops or
   repaints. It refuses lossy sources (`.webp`, `.jpg`), because
   re-encoding compounds artefacts: always promote from the PNG.
3. Add `hero` to `project.json`, run `site check`, and review the page at
   every viewport. The build only copies the committed file; it never
   runs an image tool.

A separate mobile image is not supported yet. The model leaves room for it:
`Hero` would gain an optional mobile source beside its existing mobile
focus point.

**Status:** no hero artwork has been delivered yet, so Black, Brigid and
Paranoia Engine currently use the plain header. The layout was verified with a
development stand-in test card (see `design/proof/phase-04-remediation/`).

### Previewing a hero

A hero can be previewed, with real art or a stand-in, without changing
`content/`. The preview is built from a throwaway copy of the sources in
`.local/hero-preview/` (git-ignored) and served on port 8081:

```sh
# 1. a copy of content/ and assets/ in which SLUG has a hero
docker compose --profile tools run --rm art python3 tools/art/hero_preview.py black \
    --image .local/heroes/black-hero.png --alt "…" --focus 70,35 --mobile-focus 80,45
#    (or --stand-in for a labelled layout test card with a focal target at 78,35;
#     --title/--summary to test long text; --grain [--format png --canvas 3200,1600]
#     to exercise the size policy)
# 2. build that copy
docker compose run --rm site-build stack exec -- site build --root .local/hero-preview --out .local/hero-preview/html
# 3. serve it at http://localhost:8081/work/black/ and run the dossier checks
docker compose --profile tools up -d hero-preview
docker compose --profile tools run --rm art python3 tools/screenshots/hero_check.py black NAME
```

1. Create `content/writing/{slug}/article.json` and its Markdown body (the

### Adding a résumé PDF

Put the PDF at **`content/resume.pdf`** and build. Nothing else is needed:

- it is published at **`/resume.pdf`** (a stable URL; replace the file to
  update it);
- the navigation (between About and Contact) and the footer gain a
  **Resume** link (no accent in the label), announced to assistive
  technology as "Resume (PDF)", which opens `/resume.pdf` directly;
- the build checks that it is a regular file inside `content/` (not a
  symlink out of it), that it starts with the PDF signature `%PDF-`, and
  that it is at most 10 MiB; anything else fails the build;
- it is not listed in the sitemap, which lists pages.

Without the file there is no Resume link anywhere, so the site never links
to a missing document. One résumé only; there are no role-specific
variants.

### Drafts

Draft projects and articles are still **fully validated**, so mistakes
surface early, except that a draft may use showcase kinds not yet rendered.
They produce **nothing** in `dist/`:

- no page;
- no card;
- no navigation entry;
- no link;
- no media file;
- no search data, filter chip or sitemap entry.

### Markdown

The parser is CommonMark, via `commonmark-hs`. These features are
supported:

- paragraphs;
- `##` to `####` headings;
- `*emphasis*` and `**strong**`;
- links;
- images;
- `` `inline code` ``;
- fenced code blocks, with an optional language;
- bullet and ordered lists, nested;
- block quotes;
- horizontal rules;
- backslash escapes and HTML entities, which become plain text.

Tables are not supported.

**Headings.** The page owns the `<h1>`, so a body uses `##` and below:

- `#` is an error;
- the first heading must be `##`, and levels may not be skipped;
- headings must be at the top level (not in lists or quotes);
- `#####` and deeper are errors.

Each `##` starts a section and (unless `project.json` says otherwise) an entry in the project sidebar. Text before
the first `##` becomes an unlisted lead.

**Heading ids.** Ids are derived from the heading text:

- letters and digits (any script) are kept, lowercased;
- everything else becomes single hyphens;
- if nothing is left, the id is `section`.

Repeats, and ids the page already uses, get `-2`, `-3` and so on. The
sidebar links to exactly these ids.

**Code.** Code is escaped text, readable without JavaScript, with no
syntax highlighting. Long lines scroll inside the block, never the page.

**Images.** Write `![alt text](diagram.svg)`. The path is relative to the
content item's directory, and must name an image file there:

- the allowed types are `.svg`, `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`
  and `.avif`;
- alt text is required;
- the image is published to `/media/projects/{slug}/…` or
  `/media/writing/{slug}/…`.

### Markdown HTML and URL security policy

Markdown is content, not trusted HTML.

- **Raw HTML is rejected**, inline or block, with its line number. There is
  no sanitizer.
- **Links** may only be:
  - `https://host/…`;
  - a root-absolute site path `/…`, which must resolve to a generated page
    or file (checked by the build);
  - a `#fragment`, which must name an id on the page.

  Everything else is rejected: other schemes (`javascript:`, `data:`,
  `vbscript:`, `http:`), protocol-relative `//`, relative paths, and any
  destination containing whitespace, control characters, quotes, `<`, `>`,
  backslashes or backticks. Destinations are checked after the parser
  decodes entities and escapes, so `&#106;avascript:` is caught as
  `javascript:`. Link titles are dropped.
- **Links inside emphasis or headings are rejected.** Brigid does not allow
  `<a>` there. Formatting inside link text is rendered as plain text, and
  images inside links are rejected.
- **Images** may only reference media inside the content item's own
  directory. Remote images, traversal (`..`), absolute paths, symlinks that
  escape, and non-image files such as `body.md` or `project.json` are all
  rejected.
- **Quotation marks and other punctuation are ordinary text** in summaries
  and alt text, including text that becomes an HTML attribute (the meta
  description, `og:description`, `alt`). Brigid `e0f4d45` (pinned since
  Phase 03) escapes `"`, `'`, `&`, `<` and `>` in every attribute value when
  it serializes the page, so `A "correctness-first" programming language.`
  is published exactly as written. Nothing is pre-escaped by this site.
  (The quote ban that Phase 02 added for Brigid `9344bfb` was removed in the
  post-Phase 05 remediation; `test/RemediationTests.hs` re-reads the
  rendered attributes with an independent tokenizer to prove the value stays
  inside its attribute.)
- **Defence in depth.** Every generated page is scanned before publishing:
  - every real tag (Brigid escapes `<` in text) is checked;
  - the build fails on any `on…=` event-handler attribute;
  - the build also fails on any `<script>`, `<iframe>`, `<object>`,
    `<embed>`, `<style>`, `<base>` or frame element. The single exception
    (Phase 05) is an external module script from `/assets/scripts/`,
    exactly `<script type="module" src="/assets/scripts/NAME.js"></script>`
    with no other attribute and no inline code; the file must be a listed
    asset. Only the Work index uses one.

  See [`docs/adr/0001-content-pipeline.md`](docs/adr/0001-content-pipeline.md).

## Metadata and discovery

Every page's `<head>` carries:

- `<title>` and `<meta name="description">` (the page's own title and
  summary);
- `<link rel="canonical">` and `og:url`: the production URL
  (`settingsOrigin` + the route's path);
- `og:site_name`, `og:type` (`article` for Writing articles, otherwise
  `website`), `og:title`, `og:description`, `og:locale`, and
  `twitter:card` `summary`;
- the SVG favicon.

No `og:image` or `twitter:image` is declared: no approved social artwork
exists, and a generic placeholder would misrepresent the work. Add one only
with approved art. The 404 document has `robots` `noindex` and no canonical
URL, since a static host serves it at any path.

`/sitemap.xml` lists every generated page except the 404 document, sorted
by path, with no dates (builds stay reproducible). Drafts have no route, so
they cannot appear; the résumé PDF is not a page and is not listed.
`/robots.txt` allows everything and names the sitemap. Both are generated
by `Site.Discovery` from the site's routes and appear in the manifest as
`generated` files.

To validate generated metadata: `site check` lists `robots.txt` and
`sitemap.xml` in the manifest; after a build, read `dist/sitemap.xml`,
`dist/robots.txt` and any page's `<head>`. The Haskell tests pin all of the
above, and the screenshot run checks that every sitemap URL is served and
that the canonical URL of a page is correct.

## Development workflow

### Rebuild-and-preview loop

Leave the preview running (`docker compose up -d preview`). After an edit,
run `docker compose run --rm site-build` and reload the browser. A warm
rebuild takes a few seconds. The preview serves the new files at once,
because the build replaces the contents of `dist/`, never the directory
itself.

If [`watchexec`](https://github.com/watchexec/watchexec) is installed on the
host, it can automate the loop. No custom watcher is part of the project:

```sh
watchexec -w src -w app -w assets -- docker compose run --rm site-build
```

### Removing generated output

`dist/`, `dist.tmp/` and `dist.old/` are generated and git-ignored.

- **To remove output:** stop the preview first, so its bind mount is not
  left dangling, then delete. Run `docker compose stop preview`, then
  `rm -rf dist dist.tmp`. The next build recreates `dist/`.
- **Output from before the ownership marker:** a `dist/` built before the
  marker existed is refused (`no .personal-site-output marker`). Remove it
  once, as above, and rebuild.
- **`dist.old/`:** this exists only if a build was interrupted while
  publishing, and it may hold the last good output. The build refuses to
  run while it exists. Inspect it, then delete it.
- **Caches:** `docker compose down -v` deletes the Stack cache volume. The
  next build is cold again (about 7.5 minutes).

## Accessibility, performance and deterministic captures

Phase 06 added three development-only tools. The site's own HTML, CSS and
JavaScript are never changed by them, and none of them runs in the build.
The evidence summary is in
[`design/proof/phase-06/README.md`](design/proof/phase-06/README.md).

**Accessibility audit (`tools/screenshots/phase06.py`)**

The target is WCAG 2.2 AA. Every published page, plus the fixture Writing
pages, is checked at the listed widths:

| Check | What it does | Fails when |
| --- | --- | --- |
| `axe` | axe-core 4.10.2 with the `wcag2a/aa`, `wcag21a/aa`, `wcag22aa` and `best-practice` rules, at desktop and phone | any WCAG-tagged violation. axe reports text contrast as "needs review" here, because the page-wide grain layer hides the background from it; the next check measures it instead |
| `contrast` | every text run's colour against the background pixels actually rendered under it (art, gradients, grain and the text's own dark halo), scrolled into view a half-viewport at a time; the lightest 5% of those pixels is the figure | below 4.5:1 (3:1 for large text) |
| `focusIndicator` | focuses every control by keyboard and compares the pixels that change with what they replaced (disclosures opened first) | no visible change, or under 3:1 |
| `keyboard` | a full Tab walk, then Shift+Tab back, at 1440, 390 and 320px | focus goes backwards in the document, off screen, into hidden content, or has no outline, or the walk cannot get back (a trap) |
| `targets` | every link, button, input and summary | under 24×24 px without the spacing exception (inline links in running text are exempt). Sizes under 44 px are listed too |
| `reflow` | 200% zoom (640 CSS px at scale 2), 400% (320 px at scale 4), and the WCAG 1.4.12 text-spacing overrides at 320 and 1440 px | page overflow, clipped or overlapping navigation, text past the viewport, or content cut off inside a box |
| `motion` | real motion, not the frozen capture mode | a perpetual animation, any transition under reduced motion, or a transition over 400 ms |
| `noJavaScript` | every page with scripting off | a visible button or input (inert control) or an empty container |
| `determinism` | 16 static captures, each taken twice | any capture not byte-identical |

The contrast and focus figures are measured from screenshots in headless
Chromium. They are not a substitute for a pass with a real screen reader,
which has not been done (see the Phase 06 evidence).

**Performance (`tools/screenshots/perf.py`)**

Laboratory numbers from the browser's own `PerformanceObserver` entries,
with Chrome DevTools throttling: a "Slow 4G" phone profile (390×844 at 2x,
4x CPU slowdown, 150 ms RTT, 1.6 Mbit/s) and a desktop profile. Each page is
loaded cold (empty cache) and warm, five times each, and the median is
reported. These are not field Core Web Vitals and not Lighthouse scores
(Lighthouse needs Node, which the tools image does not have). INP cannot be
measured without real interactions.

The preview server compresses text (`docker/preview.conf`) as a production
host does. Without that, the 86 KiB stylesheet dominated every phone
measurement and the numbers were unrepresentative.

**Deterministic capture mode (`tools/screenshots/stable.py`)**

Static captures used to vary between runs because some were taken while a
CSS transition was still running. Every capture tool now calls
`stable.settle(page)` before a screenshot. It runs in the test browser
only, and it:

- injects a stylesheet that cuts transitions and animations to their end
  state and hides the caret;
- loads lazy images, waits for every font face and every image to decode,
  then waits for two animation frames.

Contexts use fixed viewports, scale 1, `en-US`, UTC and a dark colour
scheme. `stable.scroll_settled(page)` waits for a real smooth scroll to
stop, instead of sleeping. Actual motion is tested separately by
`phase06.py motion`. Pages opened with JavaScript disabled are detected
synchronously (a `<noscript>` parsing probe) and frozen without waiting on
the page, since a promise that waits on such a page may never settle.

never map to one URL or file.

### Publishing and filesystem assumptions

- `DIR.tmp/` (staging) and `DIR.old/` (backup) are **siblings** of `DIR`.
  They are on the same filesystem, so each move is a `rename(2)`.
- Promotion works in three steps:
  1. Move `DIR`'s current children into `DIR.old/`.
  2. Move the staged children into `DIR`.
  3. Delete `DIR.old/`.
- **If any move fails,** the build removes the new entries, moves the old
  ones back, and reports the failure. If that rollback also fails, the
  error names `DIR.old/` as holding the previous output.
- **Atomicity:** each rename is atomic. The swap as a whole is not, so a
  request during the few milliseconds of the swap may see a mix. For a
  local build and preview, that is acceptable.
- **`DIR` itself is never replaced,** only its children. The preview
  container bind-mounts `dist/`, and that mount stays valid.
- **Output ownership.** Every build writes one extra file at the root of
  the output, `.personal-site-output`, with fixed contents. An existing
  non-empty directory is replaced **only** if that marker is present as a
  regular file (not a symlink, not a directory) with exactly those bytes.
  - A missing or empty directory is always accepted.
  - A foreign directory is refused even if it contains `index.html`, and
    so is one with a missing, malformed or symlinked marker.
  - The marker is the only non-page, non-asset file in the output. The
    Phase 07 deploy must exclude it.
- **The build also refuses an `--out` that could destroy sources:**
  - the source tree or any directory containing it;
  - anything inside `assets/`;
  - an existing file.

### Adding a fixed (non-content) page

Projects and articles need no code (see Content). For a new fixed page:

1. Add a constructor to `Route` in `src/Site/Routes.hs` and its URL in
   `routePath`. The output file follows automatically.
2. Write `src/Site/Pages/<Name>.hs` exporting `page :: SiteConfig -> Page`.
   Put exactly one `<h1>` in `pageMain`; `pageHeading` gives the house
   style. Use `Interior` layout.
3. List the page in `Site.Definition.siteFrom`. No package edits are needed:
   hpack discovers the new module.
4. Link to it with `routeUrl YourRoute`, never a string. Add it to
   `Site.Layout.navItems` only if it belongs in the primary navigation.
5. Run `site check`, then the tests. The validator fails the build if the
   new page collides with another output, links to anything not generated,
   or lacks a single `<h1>`.

New assets go in `assets/` and in `Site.Assets.allAssets`. Pages refer to
them with `assetUrl`.

### Diagnosing failures

Every failure prints `Build failed: …` and names the offending route, asset
or file. The previous output is left untouched.

| Message | Meaning and fix |
| --- | --- |
| `invalid content:` then `content/projects/x/project.json:` and field messages | Fix the named fields. Every independent problem in every file is listed |
| `field "development_status": invalid value "…"; expected one of: …` | Use one of the listed values |
| `unknown field "…"` / `missing required field "…"` | Misspelled or missing metadata (see Content) |
| `field "body": referenced file "…" does not exist` | The Markdown body named in the metadata is missing |
| `content/projects/x/body.md:` then `line N: …` | A Markdown problem at that line: raw HTML, a disallowed link, a heading-level problem, or an image without alt text |
| `… resolves to …, outside its permitted directory (symlink escape)` | A content file or media file is a symlink out of its directory |
| `field "date": invalid date "…"; that day does not exist in the calendar` | The date has the right shape but no such day (e.g. `2026-02-29`, `2026-04-31`) |
| `field "date": invalid date "…"; expected YYYY-MM-DD` | Write the date as four, two and two ASCII digits |
| `page /… contains active content in the tag …` | A tag would run script. Usually this is attribute-bound text (a summary or alt text) that itself reads like an event handler, such as `x" onclick="…`: Brigid escapes it, so it cannot break out, but the scan is a plain string check and refuses it anyway (it fails closed). Reword the text. Anything else indicates an escaping gap: report it |
| `required asset(s) missing from the source tree: - assets/images/x.webp` | A file in `allAssets` does not exist. Restore it, or remove it from the list |
| `assets/x is not a regular file` / `resolves to …, outside the assets directory` | The asset is a directory, or a symlink pointing out of `assets/`. Replace it with a real file |
| `assets/styles/site.css references "../images/x.png", which is not a listed asset` | Add the file to `allAssets`, or fix the `url()` |
| `output collision: page / -> index.html, page / -> index.html …` | Two pages share a route, or two outputs differ only in letter case. Remove or rename one |
| `output conflict: … is a file, but … needs it to be a directory` | One output's path is a directory prefix of another's |
| `asset assets/../x has an invalid path: … unsafe segment ".."` | Asset paths must be plain relative paths under `assets/` |
| `invalid slug "Brigid": …` | Use a lowercase, hyphenated ASCII slug |
| `page /about/ links to "/work/missing/": work/missing/index.html is not generated` | Fix the link, or add the page. Use `routeUrl`, not literal strings |
| `page /x/ links to "/about/#y": no element with id "y" on /about/` | The fragment target id does not exist on that page |
| `page /x/ must have exactly one <h1>, found 2` | Fix the page's heading structure |
| `refusing to write to "…": it is not empty and is not a directory this generator manages (…)` | The directory has no valid ownership marker. Use a new or empty directory, or remove this one yourself after checking its contents |
| `refusing to write to "…": it contains the source tree` (or `inside the assets directory`, `it is a file`) | The `--out` directory is unsafe (see above) |
| `"dist.old" exists, so an earlier build was interrupted while publishing` | Inspect `dist.old/` (it may hold the last good output), delete it, and rebuild |

## What happens on a clean checkout

1. **Build the image.** `docker compose build site-build` pulls the pinned
   base image and installs the two system libraries Brigid needs. The image
   contains no project source; the repository is bind-mounted at `/work` at
   run time.
2. **Cold build.** The first `docker compose run --rm site-build` creates the
   `stack-root` named volume and compiles the full dependency graph, Brigid
   included. This took about 7.5 minutes on an Apple-silicon laptop.
3. **Warm builds.** Later runs reuse the volume (and `.stack-work/` in the
   working tree) and take seconds. `docker compose down -v` deletes the
   cache volume.

The `preview` service is plain nginx serving `dist/` read-only. Its config,
[`docker/preview.conf`](docker/preview.conf), answers missing paths with
`404.html` and HTTP 404, as a static host does. It has no Haskell and no
backend, and it refuses to start if `dist/` does not exist yet.

### Inspecting the toolchain

```sh
docker compose run --rm site-build ghc --version     # 9.10.3
docker compose run --rm site-build stack --version   # 3.7.1
docker compose run --rm site-build stack ls dependencies
```

### File ownership

The container entrypoint ([`docker/entrypoint.sh`](docker/entrypoint.sh))
runs every command as the UID/GID that owns the bind-mounted repository. So
`dist/` and `.stack-work/` belong to the host user on Linux, with no `sudo` or
`chown` needed on the host.

- **Named volume:** a fresh one is root-owned, so the entrypoint hands the
  volume's top directory to that user.
- **Docker Desktop (macOS/Windows):** the VM translates ownership, so files
  land as the host user either way.

## Hero and emblem artwork

The hero plates (`assets/images/hero-plate-{left,centre,right}.webp`) are
reconstructed from the owner's approved render. The About emblem
(`about-tree.webp`) is taken from the branding board.

- **Reconstruction:** [`reconstruct.py`](tools/art/reconstruct.py) inpaints
  out all text and UI and cuts the plates.
- **Not reproducible from the repository:** the art scripts read the
  full-resolution originals from the git-ignored reference kit in `.local/`.
- **Committed outputs:** the generated images are committed source assets.
  The site build only copies them and never runs these scripts, so it stays
  deterministic.

```sh
# development-only art tooling (same tools image); outputs are committed
docker compose --profile tools run --rm art python3 tools/art/reconstruct.py     # hero plates from the render
docker compose --profile tools run --rm art python3 tools/art/emblem.py          # About tree emblem
docker compose --profile tools run --rm art python3 tools/art/compare.py         # registered render vs proof
docker compose --profile tools run --rm art python3 tools/art/monogram_sheet.py  # monogram sheet
docker compose --profile tools run --rm art python3 tools/art/promote_hero.py SLUG  # a project hero (see Hero artwork)
docker compose --profile tools run --rm art python3 tools/art/hero_preview.py SLUG --stand-in  # preview only (see Previewing a hero)
docker compose --profile tools run --rm art python3 tools/art/remediation_sheet.py   # Phase 04 remediation comparison sheets
```
