# personal-site

A personal technical folio: a static site generated by a small Haskell
executable that renders HTML with [Brigid](https://github.com/AugmenTab/brigid).
The visual language is dark Art Deco noir after the *Eclipsing Eden* brand.

**Current state: Phase 00 complete (gate passed).** One page (header,
hero reconstructed from the approved render, static Black feature teaser,
Selected Work with one project card, About with the tree emblem). See
[`DESIGN_GATE.md`](DESIGN_GATE.md) for the gate report (approved 2026-11-14) and
[`design/regression/`](design/regression/) for the approved visual baseline.
There is no Markdown pipeline, content model, or multi-page generator yet.

## Requirements

Docker Engine and Docker Compose v2. Nothing else: GHC, Stack, Cabal and all
Haskell dependencies live in the container. Screenshot tooling also runs in a
container.

## Commands

```sh
docker compose build site-build              # build the toolchain image (~1 min)
docker compose run --rm site-build           # compile + render the site into dist/
docker compose up preview                    # serve dist/ at http://localhost:8080/

docker compose run --rm site-build stack test   # Haskell smoke tests
docker compose run --rm site-build bash         # shell in the toolchain container

# development-only: screenshots + browser checks into design/proof/
docker compose up -d preview
docker compose --profile tools run --rm screenshots

# development-only art tooling (same tools image); outputs are committed
docker compose --profile tools run --rm art python3 tools/art/reconstruct.py     # hero plates from the render
docker compose --profile tools run --rm art python3 tools/art/emblem.py          # About tree emblem
docker compose --profile tools run --rm art python3 tools/art/compare.py         # registered render vs proof
docker compose --profile tools run --rm art python3 tools/art/monogram_sheet.py  # monogram sheet
docker compose --profile tools run --rm art python3 tools/art/regression.py      # vs approved baseline
```

The hero plates (`assets/images/hero-plate-{left,centre,right}.webp`) are
reconstructed from the owner's approved render, and the About emblem
(`about-tree.webp`) is taken from the branding board.
[`reconstruct.py`](tools/art/reconstruct.py) inpaints out all text and UI and
cuts the plates. Both scripts read the full-resolution originals from the
git-ignored reference kit in `.local/`, so they are **not reproducible from
the repository alone**. Their outputs are committed source assets: the site
build only copies them, and stays deterministic.

`site-build` runs [`docker/build-site.sh`](docker/build-site.sh), i.e.
`stack build` followed by `stack exec -- site build --out dist`.

### What happens on a clean checkout

1. `docker compose build site-build` pulls the pinned base image and installs
   the two system libraries Brigid needs. The image contains no project
   source; the repository is bind-mounted at `/work` at run time.
2. The first `docker compose run --rm site-build` creates the `stack-root`
   named volume and compiles the full dependency graph, Brigid included.
   This cold build took about 7.5 minutes on an Apple-silicon laptop.
3. Later runs reuse the volume (and `.stack-work/` in the working tree) and take
   seconds. `docker compose down -v` deletes the cache volume.

The `preview` service is plain nginx serving `dist/` read-only. It has no
Haskell and no backend, and it refuses to start if `dist/` does not exist yet.

### Inspecting the toolchain

```sh
docker compose run --rm site-build ghc --version     # 9.10.3
docker compose run --rm site-build stack --version   # 3.7.1
docker compose run --rm site-build stack ls dependencies
```

### File ownership

The container entrypoint ([`docker/entrypoint.sh`](docker/entrypoint.sh))
runs every command as the UID/GID that owns the bind-mounted repository, so
`dist/` and `.stack-work/` belong to the host user on Linux. No `sudo` or
`chown` is needed on the host. A fresh named volume is root-owned, so the
entrypoint hands the volume's top directory to that user. On Docker Desktop
(macOS/Windows) the VM translates ownership, so files land as the host user
either way.

## Layout

```text
app/Main.hs            CLI: site build [--out DIR]
src/Site/Assets.hs     explicit manifest of every shipped static file
src/Site/Proof.hs      the page, written with Brigid
src/Site/Build.hs      validate, then stage the output and swap it into place
test/Spec.hs           smoke tests (render, build, determinism, failure modes)
assets/                production-bound CSS, SVG, raster plates and fonts (copied to dist/assets/)
design/                design master files, curated references, proof screenshots
docs/                  PRD, implementation plan, Phase 00 handoff
docker/                entrypoint and build script for the site-build container
tools/Dockerfile       development-only tools image (never used by the site build)
tools/screenshots/     Playwright capture and browser checks
tools/art/             hero reconstruction, emblem prep, registered comparisons, monogram tools
```

The build fails, without writing output, if a manifest asset is missing or if
a stylesheet `url(...)` points at a file the manifest doesn't list.
